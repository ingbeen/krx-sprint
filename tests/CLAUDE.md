# tests 폴더 가이드

> CRITICAL: 테스트 작성/수정 전에 이 문서를 반드시 읽어야 합니다.
> 프로젝트 전반의 공통 규칙은 [루트 CLAUDE.md](../CLAUDE.md)를 참고하세요.

## 폴더 목적

tests 폴더(`tests/`)는 krx-sprint 프로젝트의 테스트 코드를 관리하며, 핵심 비즈니스 로직의 정확성을 보장합니다.

테스트 철학: 정책/불변조건/계약을 코드로 고정하여 회귀 방지

폴더 구조:

```
tests/
├── CLAUDE.md           # 테스트 규칙 (이 문서)
├── conftest.py         # 공통 픽스처 (프로젝트 진행에 따라 추가)
└── test_*.py           # 모듈별 테스트
```

`__init__.py`를 포함하지 않습니다 (src 패키지와의 이름 충돌 방지).

pytest 설정은 루트의 `pytest.ini`가 Single Source of Truth입니다.
실행 명령어는 [docs/COMMANDS.md](../docs/COMMANDS.md)를 참고합니다.

## 테스트 작성 원칙

### 1. 핵심 로직 보호

필수 테스트 대상 (= 계약/불변조건):

- 수집 도메인:
  - 스냅샷 스키마 (컬럼·dtype·티커 6자리 문자열 보존)
  - 증분 업데이트의 누락 일자 판정 (파일 존재/휴장/실패 구분)
  - 거래정지 패턴 구분 (거래량 0 + OHL 0 = 정상 플래그 / 거래량 > 0 + 가격 이상 = 예외)
  - 품질 검증 규칙 (커버리지·이상치·시총 검산)
  - 원본가/수정주가 분리 계약 (혼용 차단)
- 공통 유틸리티:
  - 메타데이터 저장/로드 (순환 저장 검증)
  - 테이블 포맷팅 (한글 폭 계산)

> 외부 API(pykrx) 호출부는 테스트에서 반드시 스텁으로 대체한다.
> 검증 게이트(스펙 §3.3)처럼 실제 API 실측이 목적인 코드는 pytest 대상이 아니라 스크립트로 분리한다.

### 2. Given-When-Then 패턴

모든 테스트는 명확한 3단계 구조를 따릅니다.

```python
def test_example(self):
    """
    목적: 무엇을 검증하는가(불변조건/계약)

    Given: 어떤 입력/상태를 준비했는가
    When: 어떤 함수를 실행했는가
    Then: 어떤 결과/부작용을 검증했는가
    """
    # Given
    df = ...

    # When
    result = function_under_test(df)

    # Then
    assert ...
```

규칙:

- "Then"은 되도록 한 가지 계약을 명확히 고정합니다.
- 복잡한 로직은 한 테스트에 여러 assert를 넣기보다, 테스트를 쪼개서 계약 단위로 고정하세요.

### 3. 경계 조건 테스트

정상 케이스뿐 아니라 엣지 케이스도 포함합니다.

- 빈 데이터 / 최소 길이 데이터 (휴장일의 빈 DataFrame 등)
- 극단값 (0, 음수, 매우 큰 값)
- 날짜 중복/정렬 불량(필요 시 입력 정규화 계약)
- NaN/결측치(정책에 따라 허용/금지 명확히)

> 중요: "엣지 케이스를 어떻게 처리해야 하는가"는 도메인 정책입니다.
> 정책이 정해져 있다면 테스트는 그 정책을 고정해야 합니다.

### 4. 결정적 테스트 (Deterministic)

테스트는 환경/시간/순서에 상관없이 항상 같은 결과를 보장해야 합니다.

- 시간 고정: `@freeze_time` 사용 (freezegun)
- 파일 격리: `tmp_path` 기반 픽스처 사용
- 랜덤성 제거: 랜덤을 쓰면 시드 고정(가능하면 랜덤 자체를 제거)
- 순서 안정화: 결과가 정렬에 민감하면 정렬 규칙을 테스트에서 명시

부동소수점/DF 비교 규칙(필수):

```python
# 금지 패턴
assert abs(a - b) < tolerance

# 필수 패턴
assert actual == pytest.approx(expected, abs=tolerance)
```

- "정확히 일치"가 정책인 값(라벨, 컬럼명, 날짜, KRX 정수 가격)은 `==`로 고정
- 모든 부동소수점 연산 결과는 `pytest.approx()` 사용이 필수
- DataFrame 비교: `pd.testing.assert_frame_equal(..., rtol=..., atol=...)`
- 배열 비교: `np.allclose(actual, expected, rtol=...)` 허용

### 5. 파일 격리

테스트는 실제 파일/실제 storage에 영향을 주지 않아야 합니다.

- 테스트에서 `storage/` 실경로(프로덕션 경로) 접근 금지
- 파일 기반 기능은 반드시 `tmp_path` 또는 경로 상수 패치 픽스처를 통해 격리
- 모듈이 import 시점에 경로 상수를 캡처할 수 있으므로(예: `meta_manager.META_JSON_PATH`),
  필요한 경우 관련 모듈도 함께 monkeypatch 합니다.

### 6. 외부 의존성 금지

- 테스트에서 네트워크/외부 API 호출 금지 (pykrx 포함)
- 환경 의존(로컬 파일, 사용자 홈, OS별 경로) 금지
- 필요하면 `monkeypatch`로 외부 호출을 스텁/대체하고, 테스트 데이터는 `tmp_path` + DF로 구성

### 7. 문서화

- Docstring 권장(테스트가 짧아도 "무엇을 고정하는지"는 남기기)
- 복잡한 계산/로직: 인라인 주석으로 단계별 설명
- 테스트 자체가 도메인 규칙의 "실행 가능한 문서" 역할

예외(에러) 테스트 규칙(권장):

- 예외 타입을 먼저 고정하고, 메시지는 정책인 경우에만 엄격하게 고정
- 일반적으로는 핵심 키워드만 `match=`로 부분 매칭

## 지속적 개선

새 기능 추가 시: 테스트 먼저 작성(가능하면 TDD) → 기능 구현 → `validate_project.py`로 회귀 방지
버그 발견 시: 재현 테스트 작성(먼저 실패 확인) → 버그 수정 → 테스트 통과 확인

사용 중인 플러그인:

- pytest-cov: 코드 커버리지 측정
- freezegun: 시간 고정 (결정적 테스트)
