## 3) 배경/맥락(Context)

### 현재 문제점 / 동기

ROADMAP Phase 4 이전 단계까지 완료돼 1단 전종목 스냅샷(2019-01-01 ~ 2026-07-24)이 확보됐다.
지표 계산(이평·전저점·스윙)은 원본가로는 분할·증자 구간에서 가짜 신호를 만들기 때문에
수정주가 시계열(2단)이 필요하다.

**계획 착수 전 사전 측정에서 스펙 §4의 핵심 전제가 반증됐다.**

로컬 스냅샷(1,856일 / 4,699,878행)만 읽어 측정한 결과(2026-07-27, KRX 호출 없음):

| 항목 | 값 |
|---|---|
| 유니크 티커 (7년 합집합) | 3,135 (마지막 일자 생존 2,764 + 폐지 371) |
| 스크리닝 수율 — 느슨 (거래대금 2배·+5%·하한 없음) | 2,979종목 = 전체의 95% |
| 스크리닝 수율 — 빡빡 (5배·+15%·하한 30억) | 2,622종목 = 전체의 84% |
| 종목별 parquet 실측 크기 | 1,856행 → 51KB (전종목 환산 약 122MB) |
| 전종목 수집 호출량 | 3,135회 ≈ 80분 |

스펙 §4는 *"통과 종목 집합은 전체의 소수 → 2단 부담 작음"*을 전제로 스크리닝 단계를 두었다.
실제로는 **7년 1,856거래일 동안 단 하루도 거래대금 급증 + 급등이 없는 종목이 거의 없어**,
어떤 파라미터를 써도 종목 수가 16% 이상 줄지 않는다. 스크리닝은 *일자* 는 크게 줄이지만
(4,699,878행 → 43,330행) *종목* 은 못 줄이며, 2단 수집 비용은 **종목 수**에만 비례한다
(종목당 1회 호출로 전 기간을 반환하므로 기간을 좁혀도 호출 수가 같다).

따라서 스크리닝 단계를 두면 파라미터 튜닝 리스크(조건 완화 시 재수집)와 코드만 남고 이득이 없다.
추가로 전종목 수집은 폐지 371종목을 **전부** 포함해 2단에서도 생존편향이 완전히 차단된다
(가장 빡빡한 스크리닝은 폐지 종목을 217개만 남긴다).

### 사용자 결정 사항 (2026-07-27, 사전 측정 결과 제시 후)

1. **수집 범위**: 스크리닝 없이 1단 합집합 전종목(3,135) 수집
2. **git 포함 여부**: `storage/adjusted/`는 **.gitignore 대상**. 수정주가는 액션 발생 시 과거 전체가
   재계산돼 파일이 통째로 다시 쓰이고, 새 거래일이 붙을 때마다 3,135개 파일이 모두 바뀌므로
   git 히스토리가 하루 100MB 이상 늘어 동기화 모델이 무너진다. 1단 스냅샷만 git에 있으면
   2단은 언제든 약 80분에 재생성 가능하다 → **스펙 §7.2 정정 필요**
3. **스크리닝 위치**: ROADMAP Phase 6(신호 로직)으로 이관

## 7) 리스크(Risks)

- **폐지 종목 개별 조회 실패**: 게이트 2는 2016년 폐지 표본 1건으로만 확인됐고, 2019년 이후 폐지 371종목 전부는 미확인이다.
  → 종목 단위로 실패를 격리해 나머지 수집을 막지 않고, 실패 목록을 조사해 스펙 §3.3의 대응 서브루틴 필요 여부를 판단한다.
  실패가 폐지 종목에 집중되면 생존편향이 2단에서 되살아나므로 **DoD를 낮추지 않고 원인을 규명한다**.

- **최신일 종가 불일치**: 수정주가가 최신일 기준으로 과거를 조정한다는 전제가 깨졌다는 뜻이다.
  → 보간·보정 없이 오류로 보고하고, 해당 종목 파일을 지운 뒤 재수집한다. 재현되면 스펙에 기록한다.
- **가변 파일 정책의 혼동**: 1단은 불변, 2단은 가변이라 조작 모델이 다르다.
  → 저장 함수 docstring·스펙·COMMANDS에 근거를 명시하고, 재수집 절차는 "파일 삭제 후 재실행"으로 통일한다.
- **git 미포함으로 인한 재생성 비용**: 다른 PC에서 백테스트하려면 약 80분 재수집이 필요하다.
  → COMMANDS.md에 절차를 명시한다. 1단이 git에 있으므로 재생성 가능성 자체는 보장된다.
- **검증 스크립트의 메모리**: 3,135파일 × 약 1,856행 ≈ 470만 행. → 티커별 스트리밍 집계로 설계하고,
