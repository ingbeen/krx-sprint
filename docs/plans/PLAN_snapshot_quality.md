## 3) 배경/맥락(Context)

### 현재 문제점 / 동기

- 수집기는 **저장 직전 인라인 검증**(음수·고가<저가·거래 중 가격 0)만 한다. 이는 한 일자 안에서의 검사이며, 일자를 가로지르는 문제는 구조적으로 볼 수 없다.
- 시범 수집에서 이미 한 건이 드러났다 — 휴장일이 정상 거래일로 저장되던 결함은 "일자 단위 검사"로는 정상이었고, 값 전체가 0이라는 **분포**를 봐야 잡혔다. 같은 종류의 문제가 더 있을 수 있다.
- 불변 파일 계약 때문에 늦게 발견할수록 되돌릴 파일이 많아진다. 2단 수집·백테스트로 넘어가기 전이 마지막 저비용 검증 지점이다.
- 스크립트는 **내부 일관성**만 검증한다. 데이터가 통째로 어긋난 경우(잘못된 일자의 값이 저장되는 등)는 외부 기준값과 대조해야만 드러나므로, 스펙 §3.1의 앵커를 검사 항목에 포함한다.

## 7) 리스크(Risks)

- **메모리**: 약 1,950일 × 약 2,200종목 ≈ 430만 행. 한 번에 올리면 수백 MB가 필요하다. → 일자별 스트리밍 집계로 설계하고, 전량 로딩이 필요한 검사는 만들지 않는다.
- **오탐으로 정상 데이터를 버리는 것**: 권리락·거래정지·신규 상장은 정상인데 이상처럼 보인다. → 심각도를 나눠 "오류"만 조치 대상으로 하고, 경고는 목록만 남긴다. 리포트는 데이터를 수정하지 않는다.
- **앵커 부족**: 스펙 §3.1에 기록된 알려진 값이 삼성전자 한 종목·한 일자뿐이다. → 이것만으로는 특정 구간의 오류를 못 잡는다. 사람이 외부 시세와 눈으로 대조하는 절차를 문서에 남기고, 확인된 값은 스펙에 앵커로 추가해 다음 검증부터 자동화한다.
- **재수집 비용**: 이슈가 광범위하면 재수집에 다시 수 시간이 든다. → 일자 단위로 선별 재수집이 가능하도록 절차를 안내한다.
- **검사 자체의 버그**: 리포트가 틀리면 오염을 놓친다. → 모든 판정 규칙을 스텁 테스트로 고정하고, 시범 수집에서 실제로 발견됐던 "전 종목 값 0" 패턴을 회귀 테스트로 포함한다.
